# 麻雀卓 新機能提案書

作成日: 2026-07-24

現状の実装(Mリーグルール対戦・LAN対戦・観戦・中断復帰・Mリーグ牌譜ビューア・👻ゴーストモード・守備/攻めアドバイザー・総合成績表)の延長線上で価値が高いと考えられる新機能を10件提案する。各項目に「概要 / ユーザー価値 / UIイメージ / 実装アプローチ(既存資産との対応) / 規模感 / リスク・留意点」を記す。

## 1. ゴースト成績の記録・比較(if検証ノート)

### 概要
ゴーストモードで局を打ち終えたとき、結果を捨てる前に「実際の牌譜の結果」と「あなたの結果」を並べて表示する。さらに同じ局面(同じ突入ポイント)での試行履歴を保存し、「この局面から5回打って 和了2 / 放銃1 / 流局2」のような分布を貯められるようにする。

### ユーザー価値
- ゴーストモードの現在の弱点は「打ち終わった結果がその場で消えて、何も残らない」こと。比較表示があるだけで「選手より良い結果を出せたか」が一目で分かり、打ち直しの動機になる。
- 全員ゴースト(if検証)と組み合わせると「ここで押した場合と引いた場合の結果分布」という定量的な検証ができる。

### UIイメージ
- 局終了オーバーレイに2カラム表示: 左「📜 実際」(牌譜DBの結果: 和了者・打点・点数移動)、右「👻 あなた」(今回の結果)。
- 「もう一度この局面から」ボタンで同じ突入ポイントに即再突入。
- 試行履歴はお気に入り局と同様の一覧画面から参照。

### 実装アプローチ
- 突入ポイントのキーは `m_league_game_id|round|honba|cutoff(_appliedEvents)` — お気に入り局のキー設計(`game_id|round|honba`)の自然な拡張。
- 実際の結果は牌譜DBの局結果レコードから取得(`ReplaySession` が既に結果画面表示に使っている)。ゴースト側の結果は `GameEngine` の局終了イベントから取得できる(現在 `_exitGhost()` で捨てている情報)。
- 保存は shared_preferences。お気に入り局(☆)と同じストア設計(リビジョン付き配列)を流用。
- `GhostRun` に局結果コールバックを1本追加し、`ReplaySession._exitGhost` の前に結果を捕捉するだけで最小構成は成立する。

### 規模感: M(比較表示のみなら S)

### リスク・留意点
- 「実際の結果」は局単位の点数移動として牌譜DBに残っているものを使う。裏ドラ枚数など表示粒度はDBスキーマに依存。
- 記録が無い巡目まで進んだ後の結果は山がシャッフルなので、分布表示には「シャッフル以降」の注記が必要。

**実装メモ(2026-09-15)**: 局終了時に左下パネルで「📜 実際: …」「👻 今回: …」を縦並び表示
(2カラムではない)。同パネルに「もう一度ここから」と、この局面の試行分布(N回: 和了/放銃/流局/他)。
試行は `lib/paifu/ghost_trial_store.dart`(キー `局キー|cutoff`)に保存。結果の捕捉は
`_exitGhost` の前ではなく局終了ビューから(`_recordGhostResult`)。試行履歴の一覧画面は無い。

## 2. 何切る出題モード

### 概要
牌譜DBからランダム(または条件指定)に局面を切り出し、「この手巡、何を切る?」と出題するクイズモード。回答後に実際の選手の選択を表示し、そのままゴーストエンジンで「実際の続き」または「あなたの選択での続き」を再生できる。

### ユーザー価値
- 23,000局超の実戦局面が出題プールになる。市販の何切る本と違い「その後どうなったか」まで見られるのが独自価値。
- 提案1(if検証ノート)と組み合わせると「出題 → 回答 → 検証」の学習ループが完成する。

### UIイメージ
- ホームに「🀄 何切る」入口。出題画面は手牌+ドラ+捨牌(河)+点数状況を静止表示。
- 手牌タップで回答 → 「選手の選択: 8p / あなた: 5s」→ 「続きを見る(📜)」「この選択で打つ(👻)」の2ボタン。
- 出題フィルタ: リーチ判断のある局面のみ / 副露判断 / 押し引き(他家リーチ後)など。

### 実装アプローチ
- 局面の切り出しは `ReplaySession._playKyoku` のイベント適用ループと同じもの(イベント列を `cutoff` 手数まで適用してビューを作る)。ビューア再生を伴わない静的版を `lib/paifu/` に切り出す。
- 「この選択で打つ」は `enterGhost` と同一機構(`buildGhostWall` + `GhostRun`)で、突入と同時に指定打牌を1手実行するだけ。
- 出題ポイントの選定: イベント列から discard イベントをランダム抽出。フィルタは reach 宣言直前 / 他家 reach 後などイベント列の走査で判定できる。
- 「良問」判定(選択肢が割れる局面)をやるならウケ枚数計算(提案4)との併用が有効。

### 規模感: M

### リスク・留意点
- 完全ランダム抽出だと「ツモ切り一択」のような自明な局面が多く混ざる。最低限「手出しした局面のみ」フィルタは必須。
- 親の第1ツモ非記録局・配牌欠落局は出題プールから除外する(既知の欠損は `buildGhostWall` の StateError で検出可能)。

**実装メモ(2026-09-15)**: 何切るは未着手。代わりに「読みクイズ」(`lib/paifu/yomi_quiz.dart`、
流局時の各家のテンパイ/イーシャンテン/それ以外と待ち牌を当てる。難易度3段階・出典表示・
ビューアで再生)を実装。本項の「イベント適用の静的版を lib/paifu/ に切り出す」は
`lib/paifu/kyoku_state.dart` として実現し、ReplaySession と読みクイズが共有している。

## 3. 自分の対局の牌譜保存・リプレイ

### 概要
対戦モード(ソロ・LAN対戦とも)の対局を牌譜として保存し、Mリーグビューアと同じUI(自動再生・ポーズ・一手送り・ゴースト)で自分の対局を再生できるようにする。

### ユーザー価値
- 「自分の放銃局をゴーストで打ち直す」が可能になる。復習ツールとして最も効果が高い。
- LAN対戦後に全員で牌譜を見返す遊び方ができる。

### UIイメージ
- ビューアのルート階層に「Mリーグ牌譜」と並べて「自分の対局」タブ。日付・メンバー・最終スコア順の一覧。
- 再生UIは既存ビューアと完全共通(☆お気に入りも共通キー設計で対応)。

### 実装アプローチ
- 記録データは既にある: 中断復帰用の `engine/resume.dart` が「局開始時の山 + 全アクション」を持つ。中断時だけでなく**毎局終了時に追記保存**するよう `GameEngine` にフックを足す(ホスト側のみ)。
- 保存形式は中断データ rev2 と同じ牌コーデック(`session/suspend_tile_codec.dart`、DB表記 '5m'/'0m'/'1z')を流用。保存先は shared_preferences では容量的に苦しいため、アプリドキュメントディレクトリの JSON/sqlite ファイルにする(牌譜DBのDL・展開機構が既に path_provider 前提で動いているので追加依存なし)。
- 再生は2案:
  - **案A(推奨)**: 保存した resume データを Mリーグ牌譜DBと同じイベント列スキーマに変換して保存し、`ReplaySession` をそのまま使う。ビューア・ゴースト・お気に入りが無改造で動く。
  - 案B: `GameEngine.fromResume` + 高速再生でその都度ビューを生成。変換不要だが ReplaySession のポーズ/一手送り/ゴーストを二重実装することになるため非推奨。
- 案Aの変換は「TurnAction/ReactAction → draw/discard/pon/chi/…イベント」の順変換で、ゴーストの `_buildScript`(逆方向の変換)と対になる。既存の `_buildScript` を参照実装にできる。

### 規模感: L(ただしビューア側は無改造で済む設計が可能)

### リスク・留意点
- イベント列スキーマへの変換が正確であることをテストで担保する必要がある。「自分の対局を保存 → 変換 → `buildGhostWall` で山が完全一致」というラウンドトリップテストが書ける(既存のゴースト用フィクスチャ整備の知見が使える)。
- LAN対戦のゲスト側は牌譜を持たない。初期実装は「ホストが保存」でよい(共有は将来課題)。

**実装メモ(2026-09-15)**: 案A/Bのどちらでもなく、`GameEngine` に内蔵したレコーダが局進行中に
本家DBスキーマ準拠のイベントを直接生成し、`lib/paifu/my_paifu_store.dart` が局ごとに保存する
(Application Support/my_paifu/ に1試合1JSON)。再生は `MyPaifuSource`(PaifuSource実装)で
ReplaySession を無改造利用(案Aの狙いは達成)。ホスト側のみ記録。ラウンドトリップは
「CPU対局を保存→再生完走」で検証(山の完全一致比較ではない)。ビューアの入口は
「🀄 自分の対局・記録した牌譜」グループ内の「🀄 自分の対局」。

## 4. 牌効率アドバイザー(ウケ枚数表示・一打評価)

### 概要
自分の手番で各打牌候補の受け入れ枚数(ウケ)を表示する。またビューア/自分牌譜の再生時に「この一打で受け入れ 24枚 → 16枚」のような一打ごとの評価を出す。

### ユーザー価値
- 既存アドバイザーは守備(SujiTable)と攻め(attackDiscard = 手戻り禁止+打点最大)だが、「何を切ればテンパイに近いか」という牌効率の定量表示が無い。初中級者への学習価値が最も高い領域。
- 提案2(何切る)の答え合わせ・良問判定にもそのまま使える。

### UIイメージ
- アドバイザーパネルに「ウケ」タブ追加: 打牌候補ごとに「打8p → 受け入れ 7種24枚(シャンテン維持)」を枚数降順で一覧。
- ビューア再生中は選手の一打に小さくバッジ表示(最大ウケ打牌なら緑、大きく損なら黄)。

### 実装アプローチ
- シャンテン数計算は既にエンジンが持っている(和了・テンパイ判定の基盤)。ウケ計算は「各候補を切る → 残り34種それぞれを引いたと仮定 → シャンテン数が下がる牌を数える」の全探索で、14×34回のシャンテン計算。既存実装の速度なら1手番あたり十分間に合う(重ければ Isolate 化)。
- 見えている牌(河・ドラ表示・自分の手)を引いて残り枚数を数える処理は SujiTable が既に持つ「見えている牌の集計」を流用。
- `advisor.dart` に `ukeireOf(hand, candidates)` を追加し、UIはアドバイザーパネルの既存タブ構造に載せる。

### 規模感: M

### リスク・留意点
- CPU 対局への流用(AIがウケ最大打牌をする)は強さバランスが変わるため、まずはアドバイザー表示のみに留め、AI強化は提案7(CPU性格)側で扱う。
- 副露手の正確なシャンテン計算(晒し分の控除)がエンジン実装でカバーされているか要確認。

**実装メモ(2026-09-15)**: `lib/engine/advisor.dart` の `ukeireMap`/`ukeireOptions` として実装。
表示はタブではなくアドバイスダイアログの非テンパイ時セクション(上位6候補)と、手牌上の
最攻撃打牌の赤グロー。ビューア再生中の一打バッジは未実装。留意点にある「CPUには流用しない」は
採らず、CPUの打牌選択にも同じウケ計算を共有した(重複実装を避ける方針を優先。
速度・強さへの影響は連戦統計で確認済み)。

## 5. 選手スタッツ・傾向ページ

### 概要
Mリーグ牌譜DBを全走査して選手ごとの副露率・リーチ率・和了率・放銃率・平均打点・平均和了巡目などを集計し、選手別ページとして閲覧できるようにする。

### ユーザー価値
- 既にDBを丸ごとローカルに持っているアプリならではの機能。「この選手は副露率が高い」を知ってからその選手の牌譜を見る、という観戦の入口になる。
- 「この選手の牌譜だけの一覧」への導線としても機能する(お気に入り試合フラット一覧の選手版)。

### UIイメージ
- ビューアの選手視点選択画面から選手名タップでスタッツページへ。
- 上段にレーダーチャート風の主要5指標、下段にシーズン別推移表と「この選手の登場試合一覧」。

### 実装アプローチ
- 集計は sqlite への集計クエリ+イベント列の軽い走査(リーチ率・副露率は reach/pon/chi/kan イベントのカウント)。23,358局の全走査は初回のみ Isolate で実行し、結果を集計キャッシュ(sqlite の別テーブル or JSON)に保存。DB更新(再DL)時にキャッシュ再構築。
- イベント列のパースはゴースト実装(`_buildScript`)で全イベント種の解釈が確立済みなので、その走査部を集計用に再利用できる。
- 既存の総合成績表UI(対戦モードのスタッツ)の表コンポーネントを流用。

### 規模感: M

### リスク・留意点
- 「放銃率」はロン和了イベントの放銃者特定が必要(discard 直後の ron)。イベント列から機械的に取れるが、ダブロン等のエッジケースをテストで確認する。
- 公式スタッツと数値がズレる可能性がある(集計定義の違い)。「本アプリ独自集計」の注記を入れる。

## 6. 観戦・ビューアの実況テロップ

### 概要
観戦UIとビューア再生に「東家がリーチ!」「残りスジ 4/18」「ドラ3の勝負手完成」などの局面イベントテロップを自動表示する。

### ユーザー価値
- ビューア自動再生の「眺める体験」が単調 → テロップで観戦らしくなる。
- SujiTable・シャンテン計算など既存の解析資産を「見せる」機能で、実装量の割に体感が変わる。

### UIイメージ
- 画面上部(リプレイ操作ボタンと干渉しない位置)に1行テロップがフェードイン→数秒で消える。
- 設定でON/OFF(観戦・ビューア個別)。

### 実装アプローチ
- テロップ発火はビュー更新ストリームの差分検知で行う: リーチ宣言・副露・ドラ増(カン)・テンパイ到達(アドバイザーのシャンテン計算を観戦視点にも適用)・残りスジ数の閾値割れ(SujiTable)。
- `lib/ui/` に `TickerOverlay` ウィジェットを追加し、GameScreen の Stack に載せる(結果オーバーレイより下、リプレイ操作より下でよい)。
- ロジックは `session` 層に `CommentaryFeed`(ビューを購読してテロップ文字列を流す)として置けば観戦・ビューア・ゴーストで共通化できる。

### 規模感: S〜M

### リスク・留意点
- 対局者本人には他家のテンパイ推測などを見せない(観戦・ビューア限定にするか、本人視点では情報を落とす)。
- ゴーストモード中は「記録とのネタバレ」になり得るテロップ(この後リーチが来る等)を出さないこと — 現在ビューから得られる情報のみで生成すれば自然に守られる。

## 7. CPUの性格・強さ設定

### 概要
ロビーでCPUごとに性格(攻め型/守備型/バランス型)と強さを選べるようにする。押し引き閾値・副露傾向・リーチ判断をパラメータ化する。

### ユーザー価値
- ソロ練習の相手に幅が出る。「守備型3人相手に攻め切る練習」のような目的別練習が可能。
- 提案8(レート)と組み合わせると「強いCPUに勝つと高レート」の設計もできる。

### UIイメージ
- ロビーのCPU枠に性格アイコン(⚔️/🛡️/⚖️)と強さ(★1〜3)のセレクタ。
- 対局中のプレイヤー表示に性格アイコンを小さく添える。

### 実装アプローチ

## 8. 段位・レート/実績バッジ

### 概要
連戦をまたぐレート(Elo風または段位ポイント制)と、実績バッジ(役満達成・国士聴牌・ハコ下勝利など)を追加する。

### ユーザー価値

- 実績はソロプレイの単調さを補う軽いゲーミフィケーション。

### UIイメージ
- ホームに自分の段位・レートを常時表示。試合終了時に「+12pt」の増減演出。
- 実績はガイドと並ぶ「🏆 実績」ページ。未達成はシルエット表示。

### 実装アプローチ
- 成績はメンバーID(`_seatMember`)で追跡する既存機構があるので、試合結果確定時にローカルプロファイル(shared_preferences)へ加算するフックを1本追加。

### 規模感: M

### リスク・留意点
- レートのインフレ/デフレ調整は難しいので、初期は「通算ポイント+段位(閾値制)」のような単調増加系が安全。
- CPU相手の試合を対人と同レートで扱うと稼ぎ放題になる — CPU戦は係数を下げる。

## 10. 点数計算クイズ / 符計算トレーナー

### 概要
和了形(手牌+ドラ+ツモ/ロン+場況)を出題し、点数(または符・翻)を答えるクイズモード。出題材料は牌譜DBの実在の和了形とランダム生成の両方。

### ユーザー価値
- ガイドに役・点数・符のページが既にあり、その実践編。点数計算はリアル麻雀への橋渡しとして需要が根強い。
- 「実在の和了形から出題」は牌譜DBを持つこのアプリならでは。

### UIイメージ
- ガイドから「🧮 点数クイズ」へ。和了形を表示 → 選択肢4択(または符・翻・点数の段階入力) → 正解表示は既存の結果オーバーレイと同じ役・符内訳フォーマット。
- 難易度: 初級(子のロンのみ・食い下がりなし)/中級/上級(符ハネ・平和ツモ等の引っかけ)。

### 実装アプローチ
- 採点はエンジンの点数計算(役判定・符計算)をそのまま呼ぶだけ — 出題UIが実装のほぼ全て。
- 実在出題は牌譜DBの和了局(tsumo/ron イベント時の手牌+晒し+ドラ)から。`buildGhostWall` 同様のイベント適用で和了瞬間の手を復元できる。
- 引っかけ問題の生成は「符が境界(30符↔40符)の形」をランダム生成でフィルタする方式が簡単。
- 正解表示コンポーネントは結果オーバーレイの役・点数表示部を切り出して共用。

### 規模感: M

### リスク・留意点
- 符計算の内訳表示(雀頭役牌+2符、辺張待ち+2符…)をエンジンが内訳付きで返せるか要確認。返せないなら内訳生成の追加実装が必要(これ自体がエンジンの点数計算テスト強化にもなる)。

## 推奨ロードマップ

独自機能であるゴーストモードを軸に、再利用率と体験向上の大きさで並べると:

1. **提案1(ゴースト成績比較)** — 最小構成なら S。ゴーストモードの価値を即座に引き上げる。
2. **提案3(自分の対局の牌譜保存)** — L だが、resume 機構と ReplaySession の資産で「保存→変換」に実装を絞れる。完成すると復習体験の核になる。
3. **提案2(何切る)** — 1と3の基盤(局面切り出し+ゴースト再突入)がそのまま出題・検証ループになる。
4. **提案4(ウケ計算)** — 2の答え合わせ・7のCPU強さの共通基盤。
5. 以降は 5+9(走査バッチ共通化でセット実装が効率的)→ 6 → 7 → 8 → 10 の順を推奨。

「検証(1) → 復習(3) → トレーニング(2・4)」と一本の線でつながり、各段が次の段の実装基盤になる構成である。

(2026-09-15 時点: 1・3・4 は完了、2 は読みクイズで代替、9 は「局を探す」で部分実装。
残りは 5・6・7・8・10。上の順序は 2026-07 時点の推奨で、現状に合わせた優先順位は未整理)

### 追記(2026-11-09) 牌譜DBダウンロードの自動再試行

iPhone 12 Pro での初回ダウンロードで GitHub から HTTP 504 が1回返り、利用者が再操作して成功した。
アプリは 200 以外を1回で諦めていたので、5xx と通信断(接続失敗・途中切断)に限って
最大3回試行(2回リトライ、待ち 2秒→4秒)するようにした(ユーザー決定: 3回駄目ならエラー表示して諦める)。
4xx は恒久的な失敗として即エラー。再試行中は「配布元の応答待ち… 再試行(2/3回目)」を表示。
HTTP 取得を差し替え可能にし、`test/paifu_download_retry_test.dart` で 504→200 成功・3連続 5xx 失敗・
途中切断の上書き・404 即失敗を固定した。

### 追記(2026-11-09) BLE ホストが iOS で開始できなかった不具合

iPhone 12 Pro で初めて BLE を試したところ、部屋作成で「BLE接続: Bluetooth の状態を取得できません」、
再作成で「BLE を開始できませんでした」になった。原因は2つ。
1. 初回の Bluetooth 許可アラートが出ている間 CoreBluetooth の状態は unknown のままだが、
   `_waitPoweredOn` が 3秒で諦めていた。上限を 60秒(`bleUnknownStateTimeout`)に延ばした。
2. ホスト側で `PeripheralManager.connectionStateChanged` を購読していたが、iOS のプラグイン
   (bluetooth_low_energy_darwin 6.2.1)はこの getter が UnsupportedError を投げる。
   try/catch で iOS では購読しない(切断は購読解除イベントで検知する既存経路のまま)。
   既存テストの偽マネージャは例外を投げなかったため見つからなかった。偽物に iOS 相当モードを足し、
   「非対応でも待ち受けできる」「unknown→poweredOn で開始」「上限超過」「拒否」をテストで固定。
あわせてホストの失敗表示に例外文を添えるようにした(原因追跡のため)。
BLE 実機検証(2026-11-09): iPhone 12 Pro(iOS 26.6.2、ホスト)⇔ Pixel 6(Android 16、参加者)で入室・対局操作が通った。
Pixel の logcat: GATT 接続 → MTU 要求 512 に対し 517 で合意 → TX 特性(bd0d86e2…)の notify 有効化 →
接続間隔 36(=45ms)。同じ Wi-Fi 上でも BLE の部屋を選べば BLE で繋がる。iPhone 同士(SE2)は未検証。

### 追記(2026-11-09) Android 卓で部屋作成が止まる(BLE 広告開始が返らない)

Pixel 6 で部屋作成に入るとインジケータが止まらなかった。logcat では GATT サービス追加(onServiceAdded status=0)
まで進み、その先の広告開始が返っていない。bluetooth_low_energy_android 6.2.1 の startAdvertising は
Advertisement.name があると先に `BluetoothAdapter.setName(name)` を呼び、ACTION_LOCAL_NAME_CHANGED を待つ。
Pixel の Bluetooth 名は 2026-09 の試験で既に「プレイヤーの卓」に書き換わっていた(settings secure bluetooth_name で確認)ため、
名前が変わらず通知が来ず、永久待ちになった。対処: Android では name を広告に載せない(端末名を書き換えない。
参加者側は「BLEの卓」と表示し入室後に部屋名を受け取る)。あわせて広告開始に 10秒の上限(`bleAdvertiseTimeout`)を
入れ、返らなくても部屋作成は他経路で続行できるようにした。テスト: 広告開始が返らない偽物で上限到達→理由文字列。
副作用の報告: Pixel 6 の Bluetooth 端末名が「プレイヤーの卓」のまま残っている(ユーザーが設定で戻す)。
逆方向も確認(2026-11-09 16:26): Pixel 6 卓 × iPhone 12 Pro 参加。Pixel の logcat で GATT サーバに
iPhone が接続(onConnectionState connected=true)→ MTU 517 まで確認。参加者側の一覧表示は「BLEの卓」。
同構成(Pixel 6 卓 × iPhone 12 Pro 参加)で 1局完走(2026-11-09 ユーザー確認)。transport-design.md §6-5 の
「iOS卓×Android参加 / Android卓×iOS参加で接続+1局」は両方向とも達成。残り: 切断→再接続、テザリング併用、iPhone 同士。

### 追記(2026-11-09) 改名された参加者が再接続で席に戻れない

BLE の切断→再接続検証で発覚(経路に依らない不具合)。ホスト「プレイヤー」と参加者「プレイヤー」が衝突すると
ホストは参加者を「プレイヤー2」に改名するが、参加者はそれを知らされず、再接続の hello で元の名前を名乗るため
切断席と一致せず観戦候補になっていた(Pixel 側では席が「プレイヤー2(代打)」のまま)。
対処: (1) ホストが入室確定時に `welcome{name}` を本人へ送り、ClientSession は以後その名前で名乗る(`name`)。
(2) アプリを入れ直して元の名前で来た場合も、切断席の中に「元の名前+数字」が1人だけなら本人とみなして戻す。
複数候補なら従来どおり観戦候補。テスト: test/net_rejoin_name_test.dart(4件)。
実機確認(2026-11-09): Pixel 6 卓 × 12 Pro BLE 参加で対局開始後、12 Pro が「退出」→「参加」で入り直し、
「プレイヤー2」の席に復帰(代打が外れた)。BLE の切断→再接続も合わせて達成。アプリ終了からの入り直しは未実施(同一経路)。

### 追記(2026-11-09) アプリアイコンを「データ牌」に差し替え

Muse(Meta AI)で作ったアイコンセットを採用。素材は assets/icon/(合成済み・前景・背景・モノクロ、各 1024px)に置き、
