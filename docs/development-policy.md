# 開発方針 — 完全バイブコーディング実験

このプロジェクト(麻雀卓)は、アプリを作ること自体に加えて
**「完全なバイブコーディングでどこまで作れるか」を経験すること**を
実験テーマにしている(2026-08-25 方針明文化)。

## 実験の枠組み

- **作者はコードを読まない。** 本当に必要でない限り、実装コードは開かない。
  普段(他プロジェクト)はAIコーディング&AIレビューでも自分でコードを読み
  手も入れるが、このプロジェクトではあえてそれを封じる。
- **git / GitHub を使わない。** バージョン管理なしで開発を進める。
  ある程度機能が固まった時点で GitHub へ初回アップする予定
  (その前に一度だけコードレビューを行う可能性はある)。
  → 2026-11-09 に `git init` と GitHub への初回 push を実施(約 4 か月、47,000 行をバージョン管理なしで
  進めた)。以後は不定期 push、push 前に公開前レビューを通す運用。コードレビューの代わりに
  行ったのは二重実装の監査と機能一覧の逆引き(README 精査)で、差分の読解はしていない。
- **他人の意見は聞かない。** 思いつきだけで、とにかく速く機能拡張を進める。
  価値基準は「自分で使って楽しいか」。他の人がどう思うかは当面放置。
- 失敗して終了しても失われるのは作者の時間だけ、と割り切っている。

## 優先順位

1. **機能拡張の速度を最重視する。** 余力は次の機能に使う。
2. **テストだけは必須。** 作者がコードを読まない以上、ロジックテストが
   「アプリが何をするはずか」の唯一の実行可能な仕様書であり、
   回帰チェックの柱になる。挙動に触れる変更には必ずテストを添え、
   既存テスト全件 + `fvm flutter analyze` を通す。
3. コードレビュー→リファクタリングという工程は日常に組み込まない。

## リファクタリングの扱い

- **AIの裁量で勝手にやってよい。** 品質を保ったまま実装工数や将来の
  拡張性を稼げるなら、提案・許可取りは不要。作者はリファクタリングが
  行われたこと自体を認知しない前提でよく、品質はテストで担保されていれば
  よい。
- 逆に、見栄えのためだけの整理に時間を使う必要はない。リファクタリングは
  目的ではなく、機能拡張の速度を買うための手段としてだけ存在する。
- バージョン管理が無いため、破壊的な変更のセーフティネットは
  既存テストを通すことのみ。挙動を変える変更ほど先にテストを厚くする。

## 品質のガードレール(最小限だが必ず守る)

| ガードレール | 根拠 |
|---|---|
| ロジックテスト全件パス | 唯一の実行可能な仕様書・回帰チェックの柱 |
| `fvm flutter analyze` クリーン | 静的な破損の検出 |
| 純粋関数の共有(CLAUDE.md §2) | 過去に重複実装がMリーグルール逸脱バグを生んだ再発防止。磨き込みではなく正しさのインフラ |
| Mリーグルールレビュー(`review-m-league-rules` スキル、CLAUDE.md §1) | ルールに触れる変更の条文突き合わせ。結果は docs/mleague-rule-review.md(条文引用が多いため非公開・手元のみ) |

## Mリーグルール専用は品質戦略でもある

一般的なコンピュータ麻雀は「ダブロンありか頭ハネか」のように多数のルールを
設定で切り替えられることが多い。本アプリは逆に**Mリーグルール以外を完全に
拒否する**(CLAUDE.md §1でAIに強制する)。これは題材の選択であると同時に、
バイブコーディングの品質を支える戦略になっている:

- **正解が外部に一意に存在する。** 「正しいか」は m-league.jp の公式規定との
  突き合わせで機械的に監査できる(ルールレビュースキルが成立するのはこのため)。
  設定可能にした瞬間、品質の問いの大半が「正しいか」ではなく検証しづらい
  「意図どおりか」に化ける。
- **分岐爆発を根元から断つ。** ルールトグルが N 個あればテストすべき組み合わせは
  最大 2^N。単一ルールならテスト全件が「この製品そのもの」を検証する。
- **逸脱が「選択肢」ではなく「エラー」になる。** ダブロン実装の失敗
  (docs/failure-log.md)が撤去一択で決着したのは、単一の正解があったから。
  設定で許す設計なら「オプションとして残す」という誤魔化しが可能だった。
- 作者がコードを読まない以上、仕様の曖昧さを飲み込む人間がいない。
  固定された外部仕様がその代わりを務める。

代償はルールの柔軟性だが、価値基準が「自分で使って楽しいか」である本実験では
その代償はゼロに近い。

## 失敗談の記録

逐次の作業ログは残さない。ただし**失敗談は docs/failure-log.md に表に出る形で
残す**(何が起きたか/どう気づいたか/変えたこと/学び)。失敗も経験値であり、
「どの種類の失敗がどの検知網に引っかかったか」がこの実験の主要な観測データ。
