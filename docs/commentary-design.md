# 実況テロップ 設計メモ(構想・未実装)

作成日: 2026-09-16。機能提案書(docs/feature-proposals.md 提案6)の具体化。
**状態: 未実装。** 実装に入る前の合意用。

## 0. 結論(段階構成)

「局面から**事実**を計算する部分」と「事実を**文**にする部分」を分け、
文にする部分を差し替え可能にする。既定はLLMを使わない。

| 段階 | 文にする部品 | 費用 | 端末 | 位置づけ |
|---|---|---|---|---|
| **段階0** | 定型文テンプレート(状況ごとに複数用意し乱数で選ぶ) | 0 | 全端末 | **既定**。これだけで機能として完結させる |
| 段階1 | OS内蔵LLM(iOS 26 の Apple Foundation Models、Android の Gemini Nano) | 0 | 対応端末のみ | 対応端末なら自動で有効。非対応なら段階0に落ちる |
| 段階2 | クラウドLLM(Anthropic API、利用者の持ち込みキー) | 従量課金 | 全端末(要ネット) | 任意設定。文章の質を上げたい人向け |

どの段階でも**事実の計算はアプリ側**(既存の純粋関数)で行い、LLMには「与えた事実を
1行の日本語にする」ことしかさせない。麻雀の判断・計算・ルール解釈をLLMに委ねない
(CLAUDE.md §1「Mリーグルール絶対」をLLMの発言にも及ぼすための構造)。

## 1. 事実の計算(全段階共通・純粋関数)

`GameView` の更新差分から「出来事」を検出し、表示用の事実を組み立てる。
ビューア(ReplaySession)・観戦(ClientSession)・ゴーストのいずれでも同じ入力で動く。

### 発火する出来事(案。頻度は要調整)

| 出来事 | 検出方法 | 添える事実(例) |
|---|---|---|
| リーチ宣言 | `lastEvent.type == 'riichi'` | 巡目・供託本数・点差・(観戦視点なら)待ち |
| 鳴き(ポン/チー/カン) | `lastEvent` | 何を鳴いたか・副露数・ドラの有無 |
| ドラ増(カン) | `doraIndicators.length` の増加 | 新ドラ・ドラ枚数の変化 |
| テンパイ到達 | シャンテン計算(観戦・ビューア視点のみ) | 待ちの種類と枚数 |
| 残りスジの減少 | `SujiTable`(既存) | 「残りスジ 4/18」 |
| 和了 | `phase == 'handEnd'` | 役・打点・順位の入れ替わり |
| 流局 | 同上 | テンパイ者・親流れ/連荘 |
| 点差の節目 | 点数の差分 | トップとの差・ラス目との差・逆転条件(既存 `comeback.dart`) |
| 局の開始 | 局番号の変化 | 場況(東n局・本場・供託) |

打牌ごとには発火しない。1局あたり数回、半荘で30〜50回が上限の目安。
連続発火は抑止(前の表示が消えるまで次を出さない、または優先度で置き換える)。

### 見せてよい情報の境界

- **対局者本人の画面**には他家のテンパイ推測・待ち・スジ残数など、本人が知り得ない
  情報を出さない(対局中の自席視点では「公開情報からの事実」だけに絞る)。
- **観戦・ビューア**では全情報を使ってよい。
- **ゴーストモード**では「記録上この後どうなるか」を含めない。入力を「その時点の
  `GameView`」に限定すれば構造的に守られる(未来の情報が入力に無い)。

## 2. 段階0: 定型文テンプレート

- 出来事ごとに言い回しを複数持ち、乱数で選ぶ。事実は差し込み(「{name}がリーチ!
  残りスジ{n}/18」)。
- 口調・長さ・頻度はここで決める(未決。§6)。
- テストは「出来事の検出」と「事実の組み立て」「テンプレートに欠けた差し込みが無い」を
  純粋関数として固定できる。乱数はシード注入で決定的にする。
- UI: 画面上部に1行、フェードイン→数秒→フェードアウト。リプレイ操作ボタン・結果
  オーバーレイと重ならない位置。設定でON/OFF(観戦とビューアで個別)。

段階0だけで機能としては完結する。以降は「同じ事実を、より自然な文にする」差し替え。

## 3. 段階1: OS内蔵LLM

### iOS 26: Apple Foundation Models

- Apple Intelligence の端末内モデル(約30億パラメータ)。自由文プロンプトで呼べる
  Swift API。日本語対応。無料・オフライン可。
- Flutter からは自前のプラットフォームチャネル(Swift側は数十行)で呼ぶ。
- 対応端末: **iPhone 15 Pro 以降 / iPhone 16 シリーズ以降**、かつ iOS 26。
- 非対応端末・Apple Intelligence 無効時は「利用不可」を返し、段階0へ落とす。

### Android: Gemini Nano(AICore)

- 対応端末: Pixel 8 以降・Galaxy S24 以降など(機種依存)。
- 要約・校正などの用途別APIは安定版だが、**自由文の Prompt API はまだ実験的**
  (2026-09 時点の認識。着手時に再確認)。安定するまで Android 側は段階0のまま
  でよい。

### 共通の設計

- 入力は §1 の事実(短いJSONまたは箇条書き)+固定の指示文(役割・口調・
  文字数上限・「与えた事実以外を述べない」)。出力は1行。
- 生成に失敗・タイムアウト(目安2秒)したら段階0の文を出す。
- テストは LLM 部分を偽物に差し替え、「呼び出しの有無・失敗時の後退」だけを固定する。
  文章の質はテストしない(できない)。

## 4. 段階2: クラウドLLM(持ち込みキー)

- Anthropic Messages API を HTTP で直接呼ぶ(Dartに公式SDKは無い。POST 1本)。
- **claude.ai の有料プランでは呼べない。** console.anthropic.com で発行する
  APIキー(従量課金)が必要。キーは利用者が設定画面に貼り、端末内にのみ保存する。
  アプリ作者側にサーバーは持たない。
- 固定の指示文を先頭に置きプロンプトキャッシュを効かせ、局面だけを後ろに載せる。
- 応答が拒否(`stop_reason: refusal`)・エラー・タイムアウトのときは段階0の文を出す。
- 通信内容は局面の事実と選手名(公人)のみ。個人情報は含まれない。

### 費用の目安(1回あたり入力600トークン・出力60トークン、2026-09 の公表単価)

| モデル | 1回 | 半荘40回 | 半荘12回(リーチ・和了・流局のみ) |
|---|---|---|---|
| Claude Opus 5 | 約0.5円 | 約20円 | 約6円 |
| Claude Sonnet 5 | 約0.2円 | 約8円 | 約2.5円 |
| Claude Haiku 4.5 | 約0.1円 | 約4円 | 約1.2円 |

為替と単価は変動する。設定でモデルと発火の粒度を選べるようにすれば、利用者が
費用を制御できる。

## 5. 懸念点

### ハードウェア

- 段階1の対応端末を**開発者が持っていない**(手持ち: iPhone 12 Pro・Pixel 6。
  どちらも Apple Intelligence / Gemini Nano 非対応)。段階1は実機が手に入るまで
  「利用不可→段階0」の経路しか検証できない。
- 端末内LLMは発熱・電池を使う。ビューアの長時間再生で連続生成すると影響が出る
  可能性がある。発火頻度の上限が必要。

### OSの制限

- iOS: Foundation Models は iOS 26 以上。ユーザーが Apple Intelligence を
  OFF にしていれば使えない。モデルのダウンロード完了前も使えない。
- Android: Prompt API が実験的で、対応機種の判定と挙動が変わり得る。
  安定版になるまで実装しない方が安全。
- どちらも OS 更新で API が変わる可能性がある(Multipeer の非推奨化と同じ種類の
  リスク)。段階0が既定であれば、LLM側が壊れても機能は残る。

### 金額

- 段階0・1はゼロ。段階2は利用者負担で、上表の規模。
- 段階2を使う人は少数と見込む。実装の手間に見合うかは、段階0・1を出してから
  判断してよい(段階2は後回しにできる構造にしておく)。

### 品質・ルール

- LLMが「数え役満」「ダブロン」のようなMリーグに無い概念を口にするリスク。
  事実の側に「役満・三倍満が上限」等の表現を含めず、LLMには事実の言い換えだけを
  させる。指示文でも「与えられた事実以外を述べない」を明記する。
- 端末内の小型モデルは日本語が崩れることがある。1行・短文・事実の言い換えに限定
  することで影響を小さくする。
- 文章の質はテストで固定できない。段階0の定型文が品質の下限を保証する。

### 権利・公開

- 選手名はDB由来の公開情報。生成文はその場で消える表示で保存しない。
- 持ち込みキーは端末内のみ。リポジトリにキーや利用者情報が入る経路を作らない
  (`pre-publish-review` スキルの検査対象)。

## 6. 未決事項(実装前に決める)

1. 口調(実況風/淡々/くだけた)と1行の文字数上限
2. 発火する出来事の最終リスト(§1 の案から取捨選択)と1局あたりの上限回数
3. 対局者本人の画面で出す/出さない(出すなら公開情報のみ)
4. 段階2を初回に含めるか、段階0(+段階1の受け皿)だけで出すか

## 7. 実装順(合意後)

1. 事実の計算(純粋関数)+出来事の検出+テスト
2. 定型文テンプレートと表示UI(ON/OFF設定込み)
3. 「文にする部品」のインタフェースと偽物による後退テスト
4. (対応端末入手後)iOS Foundation Models の橋渡し
5. (必要になれば)クラウドLLM設定画面と HTTP クライアント
